# 原型 → PRD 经验总结（供蒸馏 skill 参考）

> 来源一：才育未来项目 2026-09-24 完整实践——基于单文件高保真原型生成产品 PRD，经四轮对抗性审查（约 110 处修复）、14+1 项待决策裁决落地、原型同步改动（工具管理页/选择器改造/按钮删除）与回归审查。
> 来源二：明镜智税项目 2026-09-29 实践——基于单文件原型 + 会议转录 + 资料清单生成 PRD（v0.1→v0.4），四轮对抗性审查共修复约 44 处，其中第四轮零上下文全新审查在"已通过"章节再抓出 14 处；两轮审查代理产出的修复建议中自创的无依据数字被后续轮次抓获并回退。（下文标【明镜补】的条目来自本项目）
> 来源三：明镜智税 2026-09-29 后续实践——对终版 PRD 追加"为每条待确认事项补充编写方建议"任务，暴露了**终版之后的增量任务如何不破坏已建立的四档标签纪律**的课题（§11，标【明镜补·终版后】）。
> 本文目的：把"基于本项目的实践"蒸馏为**任何原型→PRD 任务可复用**的原则、检查点与成败经验，供后续其他原型少走弯路、少踩坑、提高一次性成功率。
> 转写约定：下文"PRD 层/三层/四层"等结构术语在 §0 定义；"DEF 清单"指原型缺陷挂账表，"DEC 表"指待决策/决策记录表；【明镜补】= 来源二，【明镜补·终版后】= 来源三。

## 0. 总纲：动手前要先想清楚的一件事

**原型是"演示真值"，不是"需求真值"。**

原型里混着三类信息，PRD 的核心工作不是"照抄原型"，而是**把这三层拆开**：

| 层 | 内容 | PRD 处理方式 |
|---|---|---|
| ① 定稿设计 | 有会议/决策文档依据 | 写成正式需求，附出处 |
| ② 原型作者的设计选择 | 未经任何人确认 | 标注出处（"原型设定"）或升级为待决策 |
| ③ 纯演示简化 | 假动作、写死数据、静态角标、固定评分 | 升级为正式需求，并挂"原型演示差异"账 |

推论：PRD 还需要**第四层——"正式版应有但原型从未做过"**（异常分支、终态之后、复核操作端、空态、退出登录等）。原型演示的几乎全是正向主流程；这一层 PRD 必须自己补，且要标注"原型未实现，属范围而非缺陷"。

**本次所有 P0/P1 级问题的根源，几乎都是这四层在起草时没有被显式分开。**

## 1. 流程模型（本次跑通的循环）

```
基线拆解（并行子代理分域精读）
→ 决策依据提取（会议/文档 → 决策台账）
→ 起草（口径说明 + 术语表 + 出处体系 + 待决策章）
→ 对抗审查轮 1：逐条对照（按章分片）
→ 对抗审查轮 2：换角度（闭环场景走查 + 术语一致性 + "不看原型能否实现"抽检）
→ 对抗审查轮 3：全文连贯终审（查多轮补丁互相打架）
→ 用户裁决待决策 → 决策落地修订
→ 落地审查轮：决议是否被正确完整落地 + 原型改动回归审查（若有）
→ 终版
```

关键设计：**每轮审查换视角，不重复同一角度**。四个正交视角（逐条对照 / 换方法扫漏 / 补丁矛盾 / 落地核查）轮着打，漏检率显著下降。

【明镜补】两个流程级补充：
- **必须保留一轮"零上下文全新审查"**：不给修复历史、不给已修清单，只给 PRD 和依据文件，以第一次见到文档的态度逐节溯源。实测：带历史的三轮审查各自通过后，零上下文的第四轮仍在"已通过"章节抓出 14 处新问题（角色命名差异、期间口径差异、行为级描述失实）——审查者拿到修复清单会聚焦"验证修复"，对未涉足区域产生阅历盲区。
- **流程必须可降级为主会话自核**：审查代理可能连续失败（认证/服务端/超时）。审查 prompt 要设计成"自带方法、依据文件清单、输出格式"，使主会话拿同一 prompt 用原文提取（python 解析 docx/xlsx + grep）即可自核，不因工具故障阻塞循环。

## 2. 起草前必须建的四件基础设施

1. **口径说明（文档头部）**：声明"本文档描述正式产品行为；原型演示差异见第 X 章；缺陷挂账见第 Y 章；待决策见第 Z 章"。这是所有后续矛盾的裁决框架——没有它，审查发现的每个问题都没有归置处。
2. **术语表**：从原型【原文】提取；**一个概念一个主称呼**（本项目实测踩坑："本章作业/环节作业/章节作业"三词同物、"训练包/资料包/课程"三词近义、"学员/学生"混用）。附辨析规则（何时用哪个词）。
3. **出处标注体系**：每条 FR 标注来源=会议定稿 / 原型设定 / 正式化新增；附"决策依据索引"附录（决策 ← 来源文档 ← PRD 落点 三列映射）。**没有出处的"定稿"字样禁止出现**（本次实测抓到"923 外审建议⑤"查无出处的溯源造假）。
   【明镜补】结论标签应为**四档**，新增"PRD 建议基线"档：起草中必然会自撰大量合理的工程默认值（删除时限、推送触发次数、SLA、字段规格），它们既非"原型设定"也非"定稿"，必须显式标为"建议基线，未经双方确认，随 X 条一并提交决策"——**禁止标"已定"**。实测踩坑：PRD 声明"争议不自行裁定"，但待决策条目的"已定"部分全是自撰内容，构成自指矛盾，第四轮才被抓出。
4. **待决策独立成章**：凡是原型和文档都定不了的口径（格式细则、动作归属、界面形态），不混进 FR 里"假装已定"，集中成表（事项/背景/建议）。用户逐项拍板后把表从"建议列"翻转为"决议列"——这个生命周期转换非常顺滑，用户拍板成本也低（见 §8）。

## 3. 基线拆解阶段的做法

- **分域并行子代理精读**（按端/模块分片），每个代理的报告强制要求四件事：
  1. 按钮/标签/提示 toast 给【原文】——这是 PRD 的术语基准，**引文被改写是高频错误**；
  2. 枚举值给全量，不给省略号；
  3. 标注"演示性假动作 vs 真实状态变更"；
  4. **强制输出"疑点"节**（命名不一致、疑似 bug、旧口径残留）。
  第 4 点是性价比最高的设计——起草前就拿到了半张缺陷清单。
- **原型架构速览先行**（视图表/动作表/state/渲染机制），后续审查代理拿到行号定位方法，效率翻倍。单文件原型注意超长行（本项目数据行 90k 字符）——在 prompt 里直接给出"用 `sed -n 'Xp' | fold -w 160` 分段看长行"的工具指引。
- **决策依据与原型并行提取**（会议纪要 → 按时间线的决策台账，关键处引用原文）。PRD 的对照基准是**双份**的：原型（做成什么样）+ 会议（为什么、哪些定了哪些没定）。

## 4. 对抗性审查的轮次设计原则

### 轮 1：逐条对照

- 按章节分片给 2~3 个审查代理，每个只管自己的章节（避免重复、避免浅尝辄止）。
- 四类问题分类：**错误**（与原型不符）/ **遗漏**（原型有 PRD 无）/ **无依据**（PRD 有原型无且查不到出处）/ **内部矛盾**。
- **每条必须带证据（行号或原文）**——这个要求让误报在回报时就能被肉眼识别。

### 轮 2：换角度（三件武器）

- **闭环场景走查**（最有效的方法）。用 6 类端到端场景推演：
  1. 新主体从零开始（新企业/新学员首登全链，含各页空态）；
  2. 注册→审批全链（**含驳回分支**——被驳回后登录/再申请怎么办）；
  3. 异常回退循环（驳回→返修→重送→再验收）；
  4. 完整生命周期到**终态之后**（结业/上线/匹配成功之后，账号与状态怎么变）；
  5. 主体切换/第二任职（换训、一人多角色）；
  6. 叙事承诺链（产品宣称的闭环，如"回流"，每处宣称是否有 FR 承载）。

  断点模式高度可预测：**正向流程都能走通，断在异常分支、终态之后、和"叙事有承诺但无 FR 承载"的地方**。
- **术语一致性专项**：对每组近义词做全文出现次数统计，列全部不一致处。
- **可读性抽检**："开发不看原型能否正确实现"——挑 3 个先开发的模块通读对应章节，缺什么报什么（字段集、校验规则、空态、错误提示）。

### 轮 3：全文连贯终审

- 多轮修补的最大风险是**补丁互相打架**。专项：同一事项在 N 处的陈述是否一致（终审前先列出该事项的全部出现点逐一比对）；表格编号/悬空引用/重复行。
- 终审结论要可执行："有条件通过：修 1 处 P1 后可定稿"，而不是泛泛的"总体良好"。

### 落地审查轮（用户裁决之后）

决议落地是**新的出错面**，专项三查：

1. **正文残留扫描**：把已决事项的旧表述、悬置措辞、功能残留全部 grep（本次"改期"功能删了 4 处后仍剩 3 处残留：联动矩阵、数据实体、缺陷表）。
2. **决议与自报落点对账**：决议表里写了"落点 13.2/FR-EP-08"，就要去那两处核实是否真的改了（本次 100MB 决议三个自报落点只落地一个——**唯一被改数的决议最容易漏落地**）。
3. 若原型同步改动：加一轮 **diff 级回归审查**（见 §7）。

### 【明镜补】修复建议回验规则（审查产出 ≠ 可写入的素材）

审查代理的输出里，**问题定位**（指出某处与依据不符）与**修复建议**（建议怎么改）可信度完全不同：定位带证据、可复核；建议是审查者新撰的文本，可能自创无依据数字与规则。实测：第一轮 23 条修复建议中有 4 处自创（"约 15-20 项核心指标""AI/专家 30-40% 精确分工""连续 2 次复检失败推送""回溯期 2024-01-01 至 2026-12-31"），照单全收写入 PRD 后下一轮才被抓获回退。

→ 规则：**采纳任何修复建议落笔前，必须回依据原文验证其每个数字与规则**；验证通过的写入时同样按 §2 的四档标签标注出处；验证不通过但方向合理的，降级为"建议基线"或进待决策，不按事实口径书写。同理，会议口径是口语转录，**模糊表述只能模糊引用**（"前期能实现 60%，只是作为一个钩子"→ 写"约 60-70% 由软件承接的钩子模式"），禁止精确化为分工比例、公式或固定日期；引用关键口径时附原文摘录。**记忆/摘要/此前会话的结论也不可信**：实测项目记忆记着"会议建议回溯 3 年"，grep 会议转录原文无此语——落笔前一律回原文 grep 验证。

## 5. 高频失败模式清单（本项目实测，按危害排序）

1. **示例数据凭记忆拼装**：PRD 里的演示数据示例混串了多个实体的字段、出现基线中不存在的值（唯一 P1 级示例错误：六字段示例把单元 1 与单元 3/4 的字段缝在一起）。
   → 规则：PRD 中的示例必须从基线**逐字拷贝**；审查轮抽查示例字段回基线核对。
2. **溯源造假/过松**：贴"定稿"标签但查无出处；把单元级结论升格为环节级定稿；把原型设计记到会议头上。
   → 规则：每个"定稿"断言在附录索引里可回溯。
3. **指控性清单误报**：DEF 清单里混入一条误报（账号统计"17 vs 16"实际是动态派生正确值），损伤整张清单可信度。
   → 规则：**指控性清单必须逐条代码级复核后才写入**，宁可少列不可错列。
4. **引文"原文"不原文**：改写、跨页拼接、把两处文案用省略号缝成一处（本次"数量不固定……必须被全覆盖"是把工作区尾注和蓝图 tooltip 缝成了一处）。
   → 规则：引文逐字校对是轮 1 必查项。
5. **把"正式版应有"写成"原型已有"**：联动、只读、标红、失败分支、动态统计——原型没做到的行为被写成现在时。
   → 规则：每个 FR 描述的行为问一句"原型真做到了吗"，没做到就挂差异/缺陷标注。
6. **枚举计数错误**："五态"列了 6 个；状态机画 7 节点（含 2 个派生态）；三套 FR 编号体系并存。
   → 规则：枚举定义后立即数一遍；编号体系起草时统一（宁可全篇都用一套）。
7. **异常分支与终态盲区**：驳回后怎么办、结业之后账号什么状态、空企业首屏。
   → 规则：用 §4 轮 2 的 6 场景模板扫。
8. **多轮修补的连锁矛盾**：每修一处，该口径在全文的其他出现点都可能变成错的。
   → 规则：**修订时先 grep 该口径的关键词，列出全部出现点再动手**；终审轮专查此类。
9. **审查代理误报死代码**：grep `data-action` 查不到写在 `data-msg`、模板字符串或内联 toast 里的按钮（本项目两次误判"完成收录""保存草稿"为死代码，实际都存在）。
   → 规则：判定"功能不存在"必须用**双证据**（定义处 grep + 全部触发语法 grep[含 data-msg/内联字符串]，最好浏览器实测），单凭一条 grep 不采信。
10. **交互形态默认"照原型"**：用户事后连续三次补充小决策（ID 不展示、官网/logo 字段、平铺改下拉多选）——都是展示形态类问题，起草时未列为待决策。
    → 规则：起草时把**展示形态类决策**（列表列名与展示字段、选择器形态[平铺/下拉/搜索]、字段扩展）显式列为待决策，不默默照抄原型。
11. 【明镜补】**审查修复建议自创数字**：见 §4"修复建议回验规则"（定位与建议的可信度差异、回原文验证流程均在彼处）。
12. 【明镜补】**证据域混同**：产品的业务范围口径（首期聚焦餐饮+洗浴）与原型的演示样例覆盖（内置高新制造/餐饮/商贸三样本）是两个维度，混写会让读者把样例覆盖当成业务优先级、或把业务优先级当成已实现能力。
    → 规则：业务范围（做哪些行业/客户）引用会议/清单；原型样例只作为流程演示载体；两处口径在同一句里同时出现时显式区分"业务优先级"与"原型样例覆盖"。
13. 【明镜补】**差异说明粒度不足**：差异章只挂"功能级"差异（toast 演示、固定样本）会漏掉更细的两级——**口径级**（同一口径多源不一：原型财报"近 2 年" vs 资料清单"近 12 期"；发票回溯年限会议/清单/原型 AI 问答三源各说不一，详见 §5.15）与**行为级**（原型快诊的关键词输入只回显不参与匹配、宣传文案"47 秒"对应动画实际数秒、免责提示原型根本不存在）。PRD 把这些写成原型现状即构成事实错误。
    → 规则：差异说明按"功能级 / 口径级 / 行为级"三层登记；PRD 中每个描述原型行为的句子问一句"原型在行为细节上真的如此吗"，并对"原型未做但 PRD 要求"的行为显式标"本 PRD 新增要求（原型未实现）"。
14. 【明镜补】**自指矛盾**：文档的自我声明（"争议不自行裁定"）与正文行为（"已定"标签、替待决策项先行拍板）冲突，各轮按清单审查时都不会主动核对声明与正文的一致性。
    → 规则：终审加一项专项——grep 正文所有"已定/默认/必须/现行基线"出现点，逐一核对是否与待决策章声明、决策方归属自洽（句式规范见 §9 质量门槛）。
15. 【明镜补】**多源口径冲突被静默取舍**：同一口径在原型、会议转录、资料清单、会话记忆中各说不一（回溯年限、财报期间），起草时随手选一个就会丢掉其余口径。本条与 §5.13 的"口径级差异"是同一问题的两面：13 管登记格式，本条管取舍纪律。
    → 规则：先穷举各源原文，正文按某一源执行时显式写"现行按 X 执行"，其余口径登记进差异说明或待确认，统一动作交给确认流程；不允许无标注的单源取舍；任何来源的转述（包括自己的项目记忆）落笔前一律回原文 grep 验证。

## 6. 冲突裁决规则（无法决议时）

- **用户指令明确的裁决优先级必须写进审查 prompt，作为第一批采集项**：本项目用户在任务开头就定了规则——"决策具有争议需要确认优先去会议内容确认，如果依然存在争议不要自我发挥，写进 PRD 的待决策单独章节"。实际裁决链是四级：**会议原文 → 原型/清单交叉验证 → 仍存争议 → 待决策章**（本项目 D1 的口径 B 即来自资料清单，仅靠会议定不了）；没有显式优先级，各审查代理会按自己的偏好裁。
- **归置结构：待决策与待确认双层**。争议事项（多方口径分歧、会议定不了）进待决策章——条目=各方口径/分歧点/建议决策方，正文不做默认处理，只写"现行基线、以决策为准"；无争议的常规确认项（客户名单、接口选型、SLA 数值）单独成"待确认"章，可逐条附编写方建议但标注规范见 §11。两层混在一起会让用户分不清"哪些要拍板、哪些只是走流程"。
- **审查代理结论之间冲突、或与基线报告冲突** → 回到证据源直接核实（grep 原型原文/行号），不采信任何中间层报告。本项目两次关键裁决（"完成收录"按钮是否存在、"保存草稿"是否死代码）都是 grep 原型原文推翻了审查员结论。
- **原型与会议文档冲突** → 会议定稿优先，原型标注为缺陷或旧口径残留。
- **原型内部自相矛盾**（同一事实多处不同源，如同一"工作结果"字段四处四种写法）→ 按缺陷挂账；PRD 以"单一数据源、一次录入多处回显"原则定稿。
- **确实无法定** → 待决策章，带背景和建议倾向；不阻塞主链路的先标注"不阻塞"，阻塞的显式标注"阻塞 FR-xxx 定稿"。

## 7. 原型同步改动的回归保障（若决议要求改原型）

- 原型每处新增导航/视图：**静态侧栏与 JS 渲染数据两处同步**（既有踩坑：JS render 会覆盖静态 HTML，漏改一处即失效）。
- 三层验证递进：
  1. `new Function(脚本全文)` 语法检查；
  2. grep 静态断言（新动作键存在、旧按钮残留=0、新文案就位）；
  3. 浏览器全流程实测：每个新交互"点开→操作→断言状态与 toast→检查 1280px 无横向溢出"。
- 浏览器断言**限定 `#main` 范围**——`body.textContent` 会命中内嵌 script 源码里的字符串字面量造成假阳性（既有踩坑）。
- **大文件删行教训**：行尾带注释的行用编辑器删除时，`old_string` 不带行尾注释会把注释拼进行尾造成隐性破坏——删行前先 grep 行尾确认。
- 改动后做 **diff 级回归审查**，会顺带发现前置存在的潜伏 bug（本次就挖出 mk.tab 双语义导致面板空白的存量 bug——新功能恰好落在该面板内，逼出了问题）。
- 给审查代理的 prompt 必须显式写"**只读分析、不做任何 git 操作**"（本次一个代理在只读任务里自行 commit 了）。
- 演示数据层面的自洽问题（如工具被引用计数用子串包含会虚高、"剪映"吃掉"剪映专业版"）：修正计数逻辑或接受为已知演示瑕疵——判断标准是"会不会误导评审读数"。

## 8. 决策生命周期管理

待决策表不是一次性垃圾场，而是一个有生命周期的资产：

```
表结构（ID/事项/背景/建议）
→ 用户裁决（可分批：本次隔了一轮又追加 3 条补充决议）
→ 翻转为（ID/事项/决议/本文落点）
→ 落点列作为自检清单（逐条去正文核实真的改了）
→ 决策记录保留在终版（后续开发争议时可回溯"为什么这样定"）
```

- 补充裁决用**增量条目模式**（DEC-15 等），不重排已有编号。
- 用户裁决可能与此前会议原意冲突（本次"列二期"推翻了 922 会议"优先做"的原话）——**如实标注分歧**（"与 922 原意存在分歧，本轮裁决为准"），不要悄悄改写历史。
- 决议落地后，第 17 章从"待决策事项"改名"决策记录"，前言写清各决议与原建议的差异——这一行前言让读者 10 秒内看懂发生了什么。

## 10. 一句话原则

> **把原型当证据库而不是需求源：起草时拆三层、引原文、标出处；审查时换四个正交视角轮着打，并至少留一轮零上下文全新审查；裁决时只信原始证据不信转述，审查的修复建议也要回原文验证后才落笔；修订时先列全部出现点再动手；终版做到"不看原型即可开发、每条结论可回溯、机械校验全过"。**【明镜补：后半句】

## 11. 【明镜补·终版后】终版之后的增量任务纪律（对"补充建议"类请求的教训）

终版不是终点。用户会在审查循环结束后追加"为待确认事项补充上你的建议"这类增量任务——它看似只是往清单里加文字，实则是对已建立的四档标签体系的一次压力测试。本节为这类任务立规矩，每条规则自带验收问句（可直接充当 skill 检查点）。

### 11.1 任务的隐藏难点

给待确认/待决策条目补充"编写方建议"时，最容易犯的错是**建议写得像结论**：一条写着"建议统一为近 3 年、截止 2026-12-31"的条目，和一条写着"回溯期为近 3 年"的条目，在读者眼里几乎没有区别——除非前者带显式免责声明。四轮审查辛苦建立起来的"读者一眼能分清已定/建议/未定"的可信度，会在这一步无声流失。

### 11.2 规则（每条句末即检查点）

1. **章首免责声明先于内容**：写第一条建议之前，先在章节头部声明"以下建议基于 X 给出推荐方向，供确认时参考，**不视为已定口径**"。声明必须在第一屏可见，不能藏在最后一条的注脚里。——检查：建议章第一屏能否看到免责声明？
2. **建议与决策的移交句式**：涉及待决策条目（D-x）的建议，必须显式写"细节见 D-x，以决策为准"——建议只能覆盖决策方未拍板的维度（推荐方向、启动方式、优先序），不能替决策方预演结论。实测写法：批量给 12 条待确认事项加建议时，涉及 D3/D4 的两条都用"按 D3 决策执行/移交"句式收尾。——检查：有无一处建议替决策方下了结论？
3. **每条建议挂出处**：写"建议 MVP 期不接真实接口"时依据的是会议"先模拟后真实"的口径；写"建议保存期不少于 3 年"时依据的是主线闭环的业务含义（税务追溯窗口）。建议不是凭空观点，每个推荐方向都应能挂到某条依据（会议/清单/方案/业务逻辑）上；挂不到的降格为"倾向性意见"并说明无依据。——检查：逐条问"这条建议的依据是什么"，答不出的是否存在？
4. **借用演示值做占位，但只能标"占位"**：算法、阈值、时限类建议可以沿用原型演示值（26/13/5、5%/20%、1 个工作日响应），但必须同时声明"初版占位、试点校准后确认"，禁止把占位值写成本轮建议的结论值。——检查：沿用演示值的建议是否都带了占位声明？
5. **增量任务同样过机械校验 + 版本递进**：补建议后重跑章节连续性/序号/引号脚本，版本号递进并更新记忆。终版后的"小改动"最容易跳过这步——正是此前序号重复（M1）的教训。——检查：这次改动跑脚本了吗？版本号动了吗？
6. **验收口径换轨 + 全文自洽**：审查循环的验收是"与依据一致"；建议补充任务的验收是"建议可辨识为建议"——随机抽一条念给不了解上下文的人听，对方能否立刻说出"这是要拍板的事，不是已定的事"？同时建议不得与正文"现行基线"表述矛盾——补的是建议，不是改口径。
