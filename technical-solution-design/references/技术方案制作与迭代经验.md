# 技术方案制作与迭代经验

## 1. 目的与证据范围

本文以本项目技术方案的制作和迭代为样本，提炼可供其他项目复用的工作方法。下文中的提交、模块、接口和数据对象属于本项目证据，不是其他项目必须采用的设计；跨项目应用时，应重新核对各自的需求、现状和约束。

本文定位为技术方案制作与迭代的跨项目方法参考，重点总结范围确认、现状核对、契约设计、依赖验证、就绪审查和实现后回写。

### 1.1 文档定位与收录边界

本文不是本项目的 PRD、技术方案、接口说明或实现状态报告。它只回答两个问题：这次迭代反复暴露了什么问题，以及其他项目可以复用什么判断方法和设计原则。

文档内容分为两层，必须明确区分：

- **通用经验层**：只写问题模式、形成原因、可迁移原则和验证方法。默认使用“业务对象、执行聚合、阶段任务、查询端口、业务绑定”等概念，不写项目类名、表名、字段名、接口路径、代码目录、具体工作台名称或当前实现状态。
- **项目证据层**：只用于证明经验确实发生过，可以记录提交号、文档路径、项目实体、具体状态和实现事实；必须放在“历史证据”“本项目案例”或附录等明确标记的区域，不能把证据中的命名直接变成通用要求。

以后新增一条经验时，先按“问题模式 → 可迁移原则 → 验证/检查方法”重写，再决定是否需要附一条单独标记的项目证据。只有为了定位证据而不可替代的具体名称才允许留在证据层；类名、字段名或当前代码是否已实现，不得出现在通用原则中。任何“当前已实现”“尚未实现”“已补齐”的判断都必须带核验时间和来源，且只能作为项目事实，不能作为跨项目结论。

## 2. 反复出现的问题

### 2.1 先写实现细节，后确认用户流程

本项目早期方案迅速覆盖了大量实体、表和接口；流程与范围进一步明确后，入口、最小交付范围和职责边界发生变化。这是常见风险：实现细节比用户问题和验收范围收敛得更快。

**经验：**先确认用户流程、验收结果和明确排除项，再展开表结构与接口。流程或范围未确认时，列为待决策，不以技术推演代替产品确认。

本项目的持久化范围曾随流程补全而扩大。可迁移的做法是先确认新增记录对应的用户流程和验收结果，再决定是否需要新的持久化对象，避免数据模型替未定的产品范围拍板。

### 2.2 “建议”“冻结”“已实现”没有分开

本项目出现过接口建议与实际实现不一致、不同方案分支的持久化范围不同，以及产品范围更新后技术方案仍保留旧口径的情况。这说明不同材料和不同成熟阶段的结论容易被混为一谈。

**经验：**为关键结论标出它是提议、待决、已确认、已实现、已取消还是已被替代，并说明依据和更新时间。描述现状时，以项目中实际运行的实现、正式接口定义和验证结果为准；方案不能把未来设计写成当前事实，也不能让过期方案继续充当现行契约。

本项目也出现了文档假设数据已结构化、实际却保存在文本中并依赖解析器提取的情况。写方案前应核对真实存储形态、已有样本和处理结果，并用代表性数据验证；不能把理想的数据结构或文档格式当作系统已经具备的能力。

如果功能触及已有 HTTP 接口、DTO、枚举、错误码、持久化对象或消息，必须先核对已有代码事实：HTTP 语义以 Controller DTO、`ProblemDetail` 和契约测试为基线，行为与持久化再结合领域实现、数据库对象和运行验证判断。文档与现状冲突时，要明确哪一方需要迁移、兼容或修复，并写出过渡期的唯一权威来源；不能只改文档或静默迁就旧实现。联调工具和其他调用方只能消费后端契约，不能自行定义状态或错误语义。

### 2.3 只设计局部成功路径，遗漏跨域交接

本项目的多次迭代暴露了上下游交接时输入无法解析、上下文缺失，以及准入规则和结果版本不清楚等问题。局部模块设计完成，并不代表端到端流程已经可实现。

**经验：**从用户操作一路追到最终使用结果的地方，检查数据如何产生、传递、保存、授权和读取。跨模块依赖应明确责任归属、调用方向、输入输出、失败处理、并发行为和必要的版本快照，并通过验收场景验证交接真实成立，不能只写“复用现有能力”。

### 2.4 状态、身份和历史数据生命周期不完整

本项目对已发布内容、可跳过步骤、准入结果和后续读取方式都经历了多轮澄清。这些问题的共同点是只定义了对象或单个状态，没有一开始说清它的责任人、生命周期以及其他对象如何依赖它。

**经验：**每个重要对象都应说明责任方、读写权限、生命周期、状态变化、不可变信息、失败或停用后的历史表现，以及下游读取实时数据还是固定版本。涉及用户身份和业务结论时，应使用可信身份来源，并在授权和确定性规则校验后再提交业务状态。

不能只定义单个状态值，还要列出多个字段之间必须同时成立的条件，以及状态组合对用户和调用方的影响。例如完成状态是否必须同时有结果和完成时间、处理期间是否可读取旧结果、跳过是否等同于通过、活动记录是否必须关联有效任务。状态值看似正确但配套数据缺失，仍会造成无法恢复或误导用户的结果。

### 2.5 外部来源和运行前置条件未经实测

本项目的外部数据接入方案后续才补充真实样本、字段映射、空结果含义、配置方式和运行前提；不同来源的许可和数据形态也影响了可采用的实现方式。

**经验：**对外部依赖，应核实使用许可、真实数据样本、稳定标识、字段缺失、限速、失败行为和运行配置。对模型或自动化服务，应使用目标环境的实际输出验证格式、解析和失败处理，不能只依赖提示词或接口说明。区分“没有结果”和“处理失败”；技术上可以访问不代表有权使用或再发布。没有证据的假设应列为待验证条件，不能静默补值。

验证还应覆盖代表性样本、空结果、未知字段、解析失败和依赖限流；未知字段应保持未知，不能让模型或业务默认值代替事实。来源、适配器、解析规则或部署配置发生变化时，必须同步检查字段映射、错误语义、测试样本和启动前置条件，并重新验证空库安装、已有库升级和启动后的真实链路。

当使用模型或异步评估时，至少分开四层：模型产生的候选输出、服务端校验后接受的不可变结果、由服务端事务决定的业务状态，以及超时、限流、解析失败等系统失败。方案必须说明各层的持久化位置、schema/模型/提示词版本、重试与重放是否追加新尝试、接受结果如何被业务引用，以及模型绝不能直接写入的身份、权限、状态、采用关系和审计字段；候选输出或系统失败不能伪装成业务成功。

采集器需要来源配置或初始数据时，应把它们作为部署契约的一部分：说明基线库和已有库分别执行哪些 SQL、脚本顺序及幂等行为，并在启用调度器前检查必需配置。政策来源曾因初始化缺失触发外键错误，后续才补来源配置和修复脚本；因此验证不能只覆盖采集代码，还要覆盖空库安装、已有库升级和启动前置检查。若接收用户提供的 URL，还需明确 SSRF 防护、协议/域名与重定向限制、网络隔离、资源上限和人工确认写入等边界；“抓取成功”不能直接成为业务记录。

### 2.6 决策变更后，旧口径仍容易残留

本项目的来源清单和多分支文档曾混有计划中、已取消、已实现的内容，也出现过彼此冲突的范围和职责描述。

**经验：**为重要决策保留一个当前结论，并记录状态、理由、替代方案和受影响材料。取消或替代一项能力后，要检查所有相关实现、配置、接口、测试材料和文档是否都已同步；不能只从计划清单中删掉，也不能只在末尾追加新说法、却让正文保留旧规则。

持久化对象或接口数量发生变化时，也要说明每个对象承担什么独立责任、为何不能由现有对象承担，以及删除后责任由谁接手。只报告数量增减，不能证明设计合理。

文档复核要检查每次修改改变了什么含义，而不只是章节是否齐全或格式是否正确。范围或契约变化后，应核对数据结构、接口、状态、权限、版本依据和实现范围，并搜索旧术语、已取消能力和互相冲突的结论。

这项清理要覆盖 PRD、技术方案、架构边界、API 和数据库计划，也要覆盖代码、测试、联调工作台、配置、脚本、原型支持文件和验证材料；取消或替代项若仍保留，必须写明保留原因、适用范围和移除条件。

### 2.7 文档完整不等于开发就绪

本项目有的方案虽然列出了主要结构和接口，数据保留、权限、合规、运维前提或交付步骤仍未决定；有的内容也明确处于待评审状态。

**经验：**就绪审计应区分已提出、已确认、已验证和已交付。会阻止实现或上线的决定、授权、合规和运行条件要单独列出并明确负责人；文档篇幅和结构完整不代表团队已经具备开工条件。

开发准入是硬门槛：任何尚未确定且可能改变实现方向的产品规则、领域边界、状态转换、历史保留、调用方、迁移、外部依赖或验收条件，都必须阻塞对应范围的开发。只有明确不影响本期范围的前置项，才可以保留为非阻塞事项，并同时写出负责人和验证点；不能用“后续再定”或文档完整度掩盖阻塞项。

### 2.8 原型演示状态不等于完整业务契约

00 统一原型是当前最小 MVP 的真实交互基线，但它仍可能包含未完成、前端本地模拟或为了演示而简化的状态。训练复核中，地图生成后的自动锁定、跳过不等于通过、评估结果进入训练对话并保留历史、附件处理完成后才能提交、能力数量为 4-8 项等规则，都是从原型和用户决策重新提炼出来的服务契约；不能看到一个按钮或一个本地状态，就反推后端已经存在对应接口。

**经验：**先把原型行为拆成“用户可见事实、服务端状态、持久化历史、异步任务、错误恢复”五列，再逐项对照代码和接口。原型没有实现的部分应标成未完成；原型中为了演示而存在的定时器、内存数组、假评分和成功提示不能进入技术方案。每次原型变化后，同时检查需求、架构、技术方案、API、测试和联调/验证环境。

### 2.9 附件对象不等于业务提交记录

执行方案中曾写明可以多次提交草稿、修订稿和补充材料，但只复用附件基础设施无法回答“这是第几次提交”“这次提交包含哪些附件”“最后采用哪次”。附件描述的是文件本身，提交记录描述的是一次业务动作；阶段完成时还需要显式指向被采用的提交，不能默认最后上传的文件就是最终结果。

**经验：**当一个文件会被多次提交、跨任务引用或在某次提交中被采用时，单独建模提交事实和附件明细。最小契约至少包含：提交主记录、提交与附件的关联快照、提交者、时间、幂等键、处理状态，以及任务上的被采用提交引用。不额外设计独立的成果版本号；用户替换材料就是创建新的提交，历史提交仍可追溯，同一个附件可以被多个阶段引用。对象数量增加必须说明独立生命周期和责任，不能用“复用现有附件”掩盖业务事实缺失。

### 2.10 关键产品决定没有转成可验证不变量

本次训练和执行讨论里，用户连续确认了“副驾可以在最低校验通过后自动完成，但不增加用户显式完成按钮”“用户可以主动跳过，跳过不伪装成完成”“跳过可继续使用能力但不计通过”“刷新后看到完整评估历史”“同一证据快照不能重复创建评估提交”“地图生成成功即锁定”等决定。若只写在说明段落里，后续很容易在 API、数据库和前端各自解释。

**经验：**每个关键决定都要落成可测试的不变量：状态转换、唯一键、错误码、历史追加规则、快照字段和可见文案分别写清。例如“通过”和“跳过”使用不同状态；同一证据快照重复提交返回 `409`；评估报告追加为不可变训练消息；附件未就绪时不创建评估任务。产品语言必须能映射到一条接口断言或数据库约束。

### 2.11 原型内容不自动构成产品实体

00 MVP 的工具生态讨论中，“指标看板模板”“访谈记录模板”等展示名称一度容易被直接解释成工具或内置模板；进一步核对后，工具通过目录中的正式工具标识识别，教学步骤由模型结合当前任务动态生成，不写入工具目录，模板功能暂缓。展示概念、领域实体、持久化模型和生成内容必须分开判断。

**经验：**先确认内容的权威来源、是否需要独立生命周期和维护责任；已有工具目录优先复用和动态查询。没有独立工作流与明确维护责任时，不因原型示例标签就增加模板库、工具字段或新表。该口径已同步到 [02 工具生态技术方案](../技术方案/02_工具生态初始化与运营后台技术方案.md)。

### 2.12 复杂度和交付批次不能只按表或接口数判断

能力训练方案最初估算 2–3 张表，随后明确了地图、版本化文件包、评估提交、跳过记录，必要时还要有证据关联；复杂度的主要增量同时来自异步生成与评估、状态转换、历史不可变、会话隔离，以及与执行域交接结果快照。表数变化反映了需求逐渐明确，但不能单独代表工作量或风险。

**经验：**按新增状态机和生命周期、异步任务与恢复、跨域授权和版本快照、外部服务与安全、历史兼容、数据库部署等维度拆解复杂度；分别指出哪些复用现有能力、哪些需要新增契约。若多个高风险维度同时变化，应先冻结共享契约，再按可独立验证的纵向流程分批交付。执行与训练在同一批提交中涉及 121 个文件、约 1.65 万行新增代码，说明大批跨域变更会增加审查和定位问题的成本；提交大小本身不能证明设计有错，但应作为拆分交付和设置阶段验收的信号。

### 2.13 跨域交接要有窄的查询契约，不能靠共享表或 Agent 工具拼接

本项目曾用“训练结果包”、上下文包或 Agent 的只读工具描述训练到执行的交接，但这些概念本身不等于进程内应用契约。执行域如果直接依赖训练表、训练域内部存储实现或评分报告表，就会把训练域的内部结构、授权规则和生命周期泄漏到下游；如果只依赖 Agent 工具，又无法保证执行入口的确定性准入和快照时点。

**经验：**跨域只暴露窄的只读查询端口（Query Port），由数据所有域在查询内部完成主体归属、版本匹配、状态准入、引用完整性和权限校验，返回下游真正需要的最小结构化快照。创建执行聚合时调用一次并冻结结果版本；后续对话轮次不实时读取可变的训练状态。查询失败、版本冲突或快照不完整时，不创建半冻结对象。Agent 的查询工具服务对话，不能替代领域间应用契约。

对演进中的项目，某个历史缺口可能在后续实现中已经补齐，因此“没有契约”只能作为带时间点的复盘结论。以后写类似结论，必须注明核验时间、实现依据和当前状态，并在方案变更后重新扫描实现、契约测试和调用方；公共经验只保留这条核验原则，不绑定具体类名、表名或接口名。

### 2.14 核心 JSON/DTO/快照只能有一份权威字段清单

执行任务的快照内容字段曾在同一套材料中先描述标题、步骤、交付物等基础字段，后文又追加阶段目标、子结果、训练能力引用等字段，但没有说明是叠加还是替换。开发者可能各自对照一处，最终导致存储结构、接口 DTO 和页面展示不一致。

**经验：**每个核心 JSON、DTO 或快照只保留一份完整的权威字段清单；基础字段和本期新增字段必须在同一处合并，并明确必填、可选、默认值、来源和语义。其他章节只引用该清单，不再复制另一版。后续扩展使用模式版本字段或等价版本策略，并为新增字段补充兼容、迁移和验收规则。发现重复字段表时，先判断两处是否冲突，再删除旧列表或改成明确的历史说明，不能靠“后文补充”让读者自行合并。

### 2.15 会话粒度与授权事实来源要分层，不要形成竞争设计

本项目出现过“一次执行一个副驾会话”和“每个阶段一个独立会话”两套说法。根因是把三个问题混在了一起：执行聚合是整次执行的容器，阶段任务是实际工作单元，会话还要解决可见性和上下文边界。当前收敛口径是每个阶段一个独立执行副驾会话。

**经验：**先分别决定聚合粒度、工作单元粒度和会话粒度，再写数据和接口。会话类型或可见性字段只负责普通列表可见性和 UI 分类；业务绑定记录负责用户、业务范围、范围版本和授权，是唯一权限事实来源。消息记录上的运行/任务标识如为查询性能冗余，必须明确只是派生索引，不能与绑定记录各自决定权限。一个项目可以选择聚合级或阶段级会话，但只能有一个冻结口径，所有需求、架构、技术方案、API 和测试必须一致。

### 2.16 范围变更要替换旧口径，开放讨论项不能伪装成冻结契约

本次执行复核中，曾出现“前文明确不做复盘、后文又要求复盘”的矛盾；当前收敛为本期做复盘，并统一包含未来展望，旧的“不做复盘”口径应删除。成果提交规则已明确，但成果提交表和 API 被留作后续讨论。前者是旧规则残留，后者是尚未冻结的设计，不能用同一种语气写进方案。

**经验：**用户确认新的范围后，应回到正文、表格、状态机、验收和检查表删除或改写旧口径，并标出替代关系和生效时间；不能只在文末追加“最新修订”。“后续讨论”“待验证”“暂不实现”必须显式标记为开放项，不得出现在当前实现清单或必做契约中。每次范围改变，都要同步检查需求、架构、技术方案、API、数据库计划、代码、测试和联调/验证环境；如果某项尚未决定，就保留边界和待决责任人，不擅自补成完整设计。

### 2.17 政策和服务生态要保持明确边界

本轮决定政策只做独立扫盲/公共信息查询，不进入方案、训练或执行的上下文装配；服务生态尚未完善，只保留必要的未来入口或留资边界，不提前冻结服务目录、供应商匹配、回访自动化和外部系统接口。此前“把政策带入方案上下文”的产品文案与当前范围冲突，必须删除。

**经验：**页面入口、展示标签和按钮只说明用户能看到什么，不自动证明已经存在对应领域实体、权限、持久化记录或外部协作流程。对尚未成熟的生态能力，只定义不越界的扩展点和本期明确的事实；等责任方、生命周期、授权和运营流程确认后再建模。政策、服务、工具、模板等名词都要先判断其权威来源和独立生命周期，避免把扫盲内容或未来入口提前写成产品契约。

### 2.18 权威来源、版本化资源和完整历史要先定义

本次复核中，同一个结果同时出现在原型状态、页面本地数据、数据库记录、异步报告、会话消息和下游快照中；如果不先定义谁是事实来源，就会出现页面显示成功但服务端没有记录、下游只拿到模糊结论、历史刷新后丢失等问题。独立生成、独立查询或独立更新的教学包、规则包、配置包和结果包，也不应长期埋在上游对象的可变 JSON 中。

**经验：**为每类事实指定唯一权威来源，并明确其他表示是投影、缓存还是冻结快照。需要保留过程的结果使用追加式历史，查询和刷新都能按原顺序回放，不能只保留“最近一次”。有独立生命周期的内容包单独版本化，由上游对象保存引用；跨域交接至少携带结果状态、来源版本、授权范围、血缘标识和未解决问题，不能只传一个布尔值或一句自然语言结论。

### 2.19 只对适用范围展开规则

技术方案不应把与功能无关的章节和复杂度硬套进来。若涉及 HTTP 交互，必须补齐方法、路径、DTO、身份授权、状态/错误语义、幂等、版本冲突和轮询或重放；若涉及持久化，必须补齐对象必要性、字段与索引、事务、并发、迁移和验证；若涉及异步、模型、外部依赖、跨域读取、安全或原型影响，也必须分别补齐对应的所有权、失败恢复、版本和验收规则。未涉及的范围明确写“不适用”，不要为了形式完整引入猜测性的实体、接口或运维负担。

### 2.20 多轮审查仍发现问题属于正常现象，回归是主导来源

一个可实施方案从初稿到收敛通常经历三到五轮独立审查。关键规律是：后续轮次发现的问题大多数不是初稿的设计缺陷，而是上一轮修改引入的回归——跨节状态口径不一致、章节插入导致的编号与引用错位、旧术语残留、同一契约在两处重复定义。初稿作者的概念完整感不等于可执行完整感；“开发者能否据此直接生成 DDL、接口定义和测试数据”这层差距，作者自查很难发现，只有独立的可实施性视角能暴露。

**经验：**把迭代循环作为流程的一部分而不是返工信号。每轮修订后立即执行一次机械回归检查（旧术语扫描、章节编号与交叉引用、重复定义、状态值一致性、敏感信息扫描），再进入下一轮复审；复审在每次重大注入（用户决议、参考实现吸收、范围变更）后必须重新触发。终止条件是“连续一轮无新 P0/P1 发现且机械检查清零”，而不是“感觉差不多了”。预算三到五轮；在第 2 轮就判定“审查无效”而提前终止，是最常见的失败方式。

### 2.21 决议回写是全文清扫，不是往决策表加一行

一条被确认的技术决议通常波及六到八处：安全配置章节、状态机、接口表、数据字典、风险登记、能力状态表、阶段门槛和审查记录。只把决议追加到决策表，正文必然残留旧口径（“待 Spike 锁定”“默认采用轮询”之类）。反过来，把开放决策粒度切得过碎也会拖慢收敛——其中相当一部分可以“建议方案 + 临时默认 + 用户否决权”的方式先收敛，等否决再改。

**经验：**为每类决议维护一张“回写触点清单”，确认后逐触点核对，而不是凭记忆改。向用户提交待决项时使用批量协议：编号（如 D-01）、冲突证据、候选方案、临时默认、责任人、关闭条件，附一行确认模板让用户一次回复关闭多项。任何决议确认后，第一动作是按触点清单全文清扫旧表述，并同步更新能力状态、阶段门槛和修订记录。

### 2.22 术语与状态词典是零号交付物

跨章节的命名与状态值漂移是多轮审查中最顽固的问题来源：同一实体在接口表和数据字典中字段名不同、任务标识在两处用不同名字、领域层大写状态与数据库/API 小写状态混用导致唯一索引谓词实际失效、同一能力两个端口各用一个名字。这类问题单条都很小，但累计起来会消耗大量审查轮次，且其中一些（索引谓词失配）会直接变成线上缺陷。

**经验：**在展开任何章节之前，先写出两份基线并让后续章节只引用不复制：一是核心实体与端口命名表，二是“领域常量 / 数据库值 / API 值”三列状态映射表。机械回归检查应包含“状态值与词典一致”这一项。发现文档中出现第二份字段清单或状态清单时，先判断是否冲突，再删除旧清单或改标为历史说明，不能靠“后文补充”让读者自行合并。

### 2.23 区分绿地与存量：未实现是任务，不是风险

在尚未进入开发的项目里，“未实现”容易被错误地当成方案阻塞项写进风险登记，仿佛方案因此不可批准；反向错误是把“被阻塞的能力”当成“排除出范围”。两者都会误导排期：前者让团队以为方案不批准就不能开工，后者让必需能力悄悄消失。

**经验：**先判断项目成熟度。绿地项目中，方案本身就是开发计划，“未实现”应进入实施任务清单并标注前置依赖与完成证据，只有外部依赖未核验、安全前提未冻结这类事项才阻断对应能力的发布，而不是阻断方案批准。为能力维护一组写进方案本体的状态词典（如“待开发未验证 / 属于本期但有前置门禁 / 隔离环境已实现 / 已交付”），并显式声明“阻塞不等于排除”。存量项目则沿用现状核对与迁移边界的既有规则。

### 2.24 参考实现按“可吸收 / 反例 / 待核验”三段吸收

存在同技术栈的参考项目时，它是效率最高的输入，也是最大的坑源：直接复制坐标、配置名和实现细节，会把对方的配置漂移、静默回退、异常吞并、未落账的成本计量和竞态窗口一起搬进来。

**经验：**对参考实现固定三段式记录：一是可吸收模式（架构边界、任务模型、事件重放、预签名双端点等），写明适配当前项目时要改什么；二是明确不照搬的反例清单，每条注明对方的问题和本项目的替代做法；三是坐标与版本只作为参考输入，标注“引入前必须按官方渠道重新核验最新版本、许可证、漏洞和兼容性”。核验只认厂商官方渠道与官方 SDK/包：厂商提供官方 Java SDK（或对应语言的官方 SDK）时必须使用官方 SDK，禁止非官方封装、社区 fork 和逆向实现；没有官方 SDK 时才允许在适配器内调用厂商官方 HTTP API，并把评审依据记录进方案。无论哪种方式，SDK/HTTP 客户端只进端口背后的适配器，领域代码不得直接依赖。参考项目的命名和契约不得直接当作本项目的事实来源。

### 2.25 事实提取并行化与交付物白名单

动笔前的事实收集量通常远超单人串行阅读的耐心，容易导致凭印象补需求；写作过程中又容易顺手修改范围外文件（规则、原型、代码），把方案任务变成实现任务。

**经验：**把事实提取拆成多个独立只读视角（需求与验收、交互与演示差异、已有契约与骨架、历史材料与冲突），并行执行并要求各视角只输出带来源的结论；写入前先汇总冲突而不是边读边改。同时为任务声明交付物白名单——本次任务允许修改哪些文件——作为硬约束写入任务说明；审查发现的问题一律修在交付物正文内，不另写审查报告，也不修改白名单之外的任何文件。

### 2.26 验收映射表是可检查的交付物，不是原则

“每条重要规则应能映射到验收场景”作为原则无法被机械检查，实际执行时经常退化为方案里的一句承诺。本次实践中，独立审查明确要求补一张“需求验收项 → 接口/模块/数据状态 → 自动化或浏览器证据 → 责任人”的映射表后，大量隐含缺口（失败分支缺失、跨端联动无证据、演示差异未覆盖）才暴露出来。

**经验：**把验收映射表作为方案的标准章节交付：逐条列出需求/决议编号、承载的接口与模块、关键数据与状态、验证方式（命令、fixture、浏览器证据）、责任人和当前证据状态；未具备证据的行必须显式标注“未验证”或“被阻塞”，不允许留空。机械回归检查包含“映射表行数与需求编号覆盖度”的核对。

### 2.27 事实源、交付留痕与高风险升级要有固定结构

方案制作中最容易漂移的三件事都没有自然落点：冲突时信谁、交付时留下什么证据、什么问题必须给人。靠逐个判断会随场景反复摇摆，靠自觉则必然遗漏。

**经验：**给每类产物指定唯一职责（需求范围 / 架构边界 / 技术决策 / 验证证据 / API 契约 / 状态机 / 数据库结构 / 代码现状），声明“同一事实只有一个正式来源，聊天记录、原型、截图、Mock 只是线索”，冲突时按职责表裁定而不是临场推理。交付时用固定字段模板（变更范围 / 修改文件 / 影响 / 未改变的关键行为 / 验证命令及结果 / 未执行验证及原因 / 未解决风险），并写明“未执行不等于通过”。维护高风险人工评审清单（认证与授权、不可逆数据操作、公共契约与状态机、外部系统接入、租户隔离与敏感数据、依赖与回滚策略），触及即升级给人，不允许自闭环。

## 3. 推荐制作流程

| 阶段 | 必做事项 | 退出条件 |
|---|---|---|

| 7. 一致性复核与迭代循环 | 对照需求、设计、接口、数据、实现计划、调用方、测试和运维安排，查找重复字段清单、旧术语、冲突口径和跨域越权路径；按实际涉及范围执行条件化审计，并扫描取消项的代码、配置和验证残留；每轮修订后执行机械回归（旧术语、章节引用、重复定义、状态值与词典一致性、敏感信息），重大注入后重新触发复审，直到连续一轮无新 P0/P1 且机械检查清零 | 只有一个当前结论；提案和历史修订已标注状态；当前代码状态已按时间点重新核验；无会改变实现方向的未决项；机械检查清零 |
| 8. 实现后回写 | 按实际修改核对方案；记录偏差、原因和验证证据，更新受影响的设计、调用方和测试材料；交付记录用固定字段模板（变更范围 / 修改文件 / 影响 / 未改变行为 / 验证命令及结果 / 未执行验证及原因 / 未解决风险），未执行不写成通过 | 文档描述当前事实，历史决策仍可追溯且不再冒充当前口径；未执行验证均有原因可查 |


一致性复核应包含语义比较：对数据、接口、状态、权限、版本和实现范围的每项变化，检查上下游材料和测试是否同步；对于取消或替代项，确认相关实现和验证材料没有残留。数据对象或接口数量变化必须附带责任和生命周期理由。

## 5. 值得保留的成熟做法

- 先记录现有边界和不受影响的行为，防止新需求无意扩大身份、权限或既有系统的责任范围。
- 用契约表、状态转换和验收场景替代含糊的“调用某服务即可”。
- 不确定性较高的自动化输出先作为候选；完成校验和授权后再更新业务状态，跨模块交接只传递必要且可追溯的数据。
- 用决策记录呈现当前结论、默认处理和待验证项；实施后说明实际变化及其验证依据。
- 对失败、重试和回放定义清楚副作用边界；重要能力分阶段交付，并说明如何停用或恢复。
- 先建术语与状态词典再展开正文；每轮修订后跑机械回归，把“多轮仍发现问题”预期为回归主导的正常现象而不是审查失效。
- 决议确认后的第一动作是按触点清单全文清扫，而不是往决策表追加一行。
- 事实提取并行只读、交付物白名单硬约束，把“读”和“改”严格分开。
- 事实源职责表裁定冲突；交付留痕用固定字段模板，未执行的验证写原因而不是写成通过；高风险类别触及即升级人工评审。
