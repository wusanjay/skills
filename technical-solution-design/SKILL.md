# Technical Solution Design

Turn an existing product definition into a coherent technical solution that engineers can build and integrate. Treat the PRD as the product-scope source, the prototype as interaction evidence, the selected stack as an engineering constraint, and the repository as evidence of what already exists. Resolve conflicts explicitly; never silently promote a demo detail, legacy behavior, or technical preference into a product rule.

The primary deliverable is the technical solution. Maintain shared boundary/contract and upstream/downstream impact documents when the feature affects them. Review the existing PRD for alignment, but do not rewrite it by default. Do not create a standalone feature prototype or implement production code.

## Boundaries

- Read repository instructions, inspect the worktree, and preserve user changes before editing.
- Use project terminology, document conventions, selected stack, and existing architecture. Do not import another project's paths, technologies, database process, naming, or domain examples as requirements.
- Do not infer authorization for production changes, schema application, external-system mutations, or edits to existing prototypes. Stop and ask when a material user decision or permission is required.
- Distinguish existing implementation facts, confirmed product decisions, recommended defaults, assumptions, open decisions, and implementation prerequisites.
- Expand only applicable concerns. For an unrelated concern, omit speculative design; say “not applicable” when needed to make the scope explicit.

## Workflow

1. **Establish the baseline.** Read repository and target-directory instructions; inspect `git status`; find the PRD, prototype and its supporting files, selected-stack decision, architecture/design documents, and relevant scaffold/code/tests. Assign each artifact class a single owning responsibility (requirements scope, architecture boundaries, technical decisions, verification evidence, API contract, state machines, database structure, current code state) — one fact, one formal source. Chat records, prototypes, screenshots, mocks, and scratch scripts are clues only, never directly a production behavior, permission, database structure, or API contract. When two sources conflict, the ownership table decides whom to trust. Identify the feature boundary and behavior that must remain unchanged. If an expected input is missing or contradictory, record that fact instead of inventing it.

2. **Reconcile product evidence.** Extract the user's goal, flows, observable behavior, scope, exclusions, acceptance criteria, and upstream/downstream relationships from the PRD. Inspect relevant prototype states and interactions, but classify them as confirmed product behavior, demo-only simulation, incomplete evidence, or conflict. A timer, local state, mock result, success toast, or visible label is not by itself a service contract or domain entity. Treat selected technologies as constraints, not as proof that a particular architecture is required. When fact-finding is large, split it into independent read-only passes (requirements/acceptance, interaction/demo deltas, existing contracts/scaffold, historical materials/conflicts), run them in parallel, and reconcile conflicts before drafting; enforce a deliverable allowlist so the task edits only the solution artifact, and fix findings in the artifact body rather than in a separate review report.

3. **Establish the glossary and status lexicon before drafting.** Before expanding any section, write a naming table for core entities and ports, and a status mapping table with three columns: domain constant, database value, API value. Later sections reference these tables instead of copying them. This prevents the most persistent multi-round defects: field-name drift between API tables and data dictionaries, dual names for one identifier, and case-mismatched status values that silently invalidate unique-index predicates.

4. **Resolve direction-changing decisions before drafting.** Maintain a compact decision ledger covering confirmed decisions, recommended defaults, open decisions, assumptions, exclusions, implementation prerequisites, evidence/source of truth, and affected artifacts. Give each new dependency a ledger entry recording: source channel, officiality (official SDK / official HTTP API / other, with review rationale if not official), version, license, maintenance status, reason for introduction, and review conclusion. Record each open decision as: id, conflict evidence, candidate options, temporary default, decision owner, and closure condition. Resolve repository facts yourself. Ask the user only about decisions that materially change user behavior, ownership, persistence/history, compatibility, security, or recovery — preferably as one batch with recommended defaults and a one-line confirmation format, rather than serial questions. Escalate findings that touch any of the high-risk review classes to a human reviewer regardless of confidence: authentication/authorization and token lifecycle, database structure or irreversible data operations, public APIs / shared types / state machines, external-system integration, tenant isolation / sensitive data / audit / idempotency, and dependency / cost / rollout-or-rollback strategy changes. Do not disguise such a decision as a technical default or freeze it as a contract. When a decision is confirmed, the first action is a full write-back sweep across its touchpoints (security/auth sections, state machines, API tables, data dictionary, risk register, capability statuses, phase gates, revision log) to remove stale wording — not just appending a row to the ledger.

5. **Map contracts and impacts.** Trace the flow from confirmed entry through producers, owners, interfaces, persistence, consumers, and final user-visible result. For each shared concept, identify the owning side and consuming side, data provenance, authorization source, version/lifecycle, failure propagation, and rollout dependency. Do not invent callers or integrations. Maintain shared boundaries/contracts and upstream/downstream impact documents only where the change is genuinely cross-cutting; keep one canonical definition for shared facts.

6. **Write the technical solution.** Make it specific enough to implement and integrate while adapting the structure to this feature. State existing versus proposed behavior, decisions and exclusions, affected components, sequence/state rules, contracts, data ownership, compatibility, validation, rollout and operational risks. Explain the smallest-impact viable design and its residual risks. For each core resource, say what it belongs to, how many may exist, when it is created, whether it can be regenerated or overwritten, who owns its version, and how history resolves it.

7. **Run the adversarial review as an explicit loop, not a single pass.** Each round: (a) run cross-review across the existing PRD, the technical solution, and shared boundaries/contracts plus upstream/downstream impact — checking product rules against interfaces, DTO fields/types/enums, state and error semantics, ownership, authorization, versioning, cardinality, creation/regeneration/overwrite rules, history, failure/recovery, compatibility, and acceptance coverage; (b) fix accepted findings in the source documents, never in a separate review report; (c) immediately run a mechanical regression sweep — stale-term scan, section numbering and cross-references, duplicate definitions, status values against the lexicon, sensitive-information scan. Re-trigger a full review round after every major injection (user decisions, reference-implementation absorption, scope change). Expect three to five rounds: later-round findings are dominated by regressions from earlier edits, which is normal and not evidence that review is failing. Terminate only when a full round yields no new blocking findings and the mechanical sweep is clean.

8. **Check prototype impact after review.** Compare the agreed behavior against the relevant existing prototype and supporting files. Record affected screens/entries, state calculation, buttons, copy, mock data, timers, and local state, and distinguish product rules from demo-only behavior. If edits to an existing prototype are warranted, ask the user before changing it. Do not treat prototype modification as an implicit deliverable.

9. **Absorb reference implementations in three segments when one exists.** For a same-stack sibling project: record absorbable patterns (and what must be adapted for this project), an explicit anti-pattern list of that project's known defects with the replacement approach here, and dependency coordinates as reference inputs only — marked as requiring re-verification against official channels (latest version, license, vulnerabilities, compatibility) before adoption. Verification accepts only the vendor's official channel and official SDK/package: when the vendor provides an official SDK, use it — no unofficial wrappers, community forks, or reverse-engineered implementations; only when no official SDK exists may the adapter call the vendor's official HTTP API, with the review rationale recorded in the solution. Either way, the SDK/HTTP client stays inside the adapter behind a port; domain code never depends on it. Never treat the reference project's names, config keys, or contracts as facts of this project.

10. **Assess development readiness.** Apply the conditional audit below. Documentation length or a complete-looking outline is not evidence of readiness. Identify what can proceed in parallel, what blocks implementation/integration, what is intentionally deferred, and the highest-severity remaining blocker. Do not claim readiness while an unresolved issue could change implementation direction. For a project that has not entered development (greenfield), "not implemented" is expected: put those items in the implementation checklist with prerequisites and completion evidence instead of the risk register, and only external-dependency or security-precondition gaps block the affected capability's release — not the plan's approval. Maintain a capability status vocabulary in the artifact itself (e.g., planned-unverified / blocked-with-prerequisites / delivered-in-test-only / delivered) and state explicitly that "blocked does not mean out of scope."

11. **Deliver the acceptance mapping as an artifact.** Include a table mapping each requirement/decision id to its owning API/module, key data and states, verification method (command, fixture, browser evidence), owner, and current evidence status. Rows without evidence must be explicitly marked "unverified" or "blocked"; no blank rows.

12. **Verify and hand off.** Re-scan for stale terminology and conflicting conclusions across affected artifacts; verify shared fields and state rules field by field. Run appropriate document/diff checks. Deliver the handoff in a fixed record: task/requirement id, change scope, files modified, interface/data/permission impact, key behavior deliberately unchanged, verification commands and results, verification not performed and why, unresolved issues and risks. State explicitly that a check not run is a check not passed — never describe an unexecuted command as passing. Report prototype impact/permission status, readiness conclusion, and remaining decisions or prerequisites. Keep the overview concise and in plain language.

## Conditional Design Rules

- If the feature involves HTTP interaction, define method/path, request and response shapes, authentication/authorization, success and error semantics, idempotency, version/conflict behavior, and polling/event/replay behavior as applicable.
- If it changes persistence, enumerate new, changed, reused, and removed objects/fields/indexes and migrations/backfills, or explicitly state there is no data change. Explain each object's necessity, ownership, transaction boundary, uniqueness/concurrency behavior, mutability, history, migration and verification. Follow the target project's database delivery policy; do not assume one.
- If it involves a model or asynchronous evaluation, distinguish candidate output, server-accepted immutable result, business state, and system failure. Define persistence, schema/model/prompt versions, retry/replay history, deterministic validation, authorization, and fields/states the model must never write. Candidate output or dependency failure must not masquerade as business success.
- If it depends on external data/services, verify representative real samples, permissions/licensing, field meaning, stable identifiers, missing/unknown fields, empty results, parse failures, rate limits, runtime configuration, and recovery. Unknown facts stay unknown; do not silently infer or default them. Re-check adapters, mappings, errors, samples, deployment prerequisites, and tests when the dependency changes.
- If it crosses domains/modules, define the narrowest useful provider-owned contract, caller/consumer, ownership and authorization, snapshot/version point, failure behavior, and compatibility. Do not substitute shared-table access, copied internal DTOs, or conversational tools for a deterministic application contract.
- If security, privacy, or user-supplied input is involved, state trust boundaries, authorization source, validation, abuse/resource limits, sensitive-data handling, and failure behavior appropriate to the risk.
- If the existing prototype is affected, classify each relevant behavior as confirmed, demo-only, incomplete, or conflicting; ask before editing it.
- If a concern does not apply, do not add speculative entities, interfaces, or operational burden merely to fill a template.

## Development Readiness Gate

Audit only applicable concerns and distinguish `defined`, `implemented`, `integrated`, and `verified`; documentation alone cannot establish implementation or verification. For affected existing contracts, inspect declaration, concrete implementation, wiring, callers, tests, and referenced data objects rather than inferring completeness from an interface or design document.

Any unresolved product rule, ownership/boundary, state transition, history/retention rule, caller/consumer, migration, compatibility condition, dependency behavior, or acceptance scenario that could change implementation direction blocks the affected implementation scope. A prerequisite may remain non-blocking only when it does not affect the agreed scope and has an owner and verification point.

Greenfield distinction: for a project that has not entered development, "not implemented" is not a blocker to plan approval — those items belong in the implementation checklist with prerequisites and completion evidence. Only unverified external dependencies or unfrozen security preconditions block the affected capability's release. A solution may be approved as a development baseline while its release conclusion remains blocked.

End the readiness assessment with four explicit conclusions:

- Work that can proceed in parallel.
- Work that must finish before implementation or integration.
- Intentionally deferred work and its boundary.
- The highest-severity blocker, or an explicit statement that none remains.

## Completion Check

- The PRD remains the product rule source; prototype evidence and scaffold facts are correctly classified.
- The technical solution and affected shared contracts/impact materials agree on terminology, fields, types, states, errors, ownership, authorization, versions, exclusions, and lifecycle.
- The glossary and status lexicon (entity/port naming, domain-constant/database-value/API-value mapping) exist, and no section carries a second copy or a value that contradicts them.
- Every confirmed decision has been swept across its touchpoints (auth/security sections, state machines, API tables, data dictionary, risk register, capability statuses, phase gates, revision log) with no stale wording left.
- Each material rule maps to a relevant acceptance or verification scenario; the acceptance mapping table is delivered with no blank evidence cells (rows are marked "unverified" or "blocked").
- Applicable failure, retry/replay, concurrency, history, migration, compatibility, security, and rollout conditions are implementable; irrelevant concerns were not invented.
- Reference-implementation absorption, if used, records absorbable patterns, anti-patterns with replacements, and coordinates pending official re-verification.
- External-system integration states its implementation choice: official vendor SDK (mandatory when one exists) or vendor official HTTP API with recorded review rationale, confined to an adapter behind a port — no unofficial wrappers, forks, or reverse-engineered clients, and no domain-level SDK dependency.
- The review loop terminated per its criteria: no new blocking findings in the final round and the mechanical regression sweep is clean.
- The final handoff uses the fixed record (scope, files, impact, unchanged behavior, verification commands/results, not-performed with reasons, unresolved risks), and no unexecuted check is described as passing.
- Every new dependency has a ledger entry: source channel, officiality, version, license, maintenance status, reason, review conclusion.
- Findings touching the high-risk classes (auth, irreversible data, public contracts, external integration, tenant/sensitive data, dependency/rollout strategy) were escalated to a human reviewer rather than self-closed.
- Open decisions and prerequisites are visible, and development readiness follows the hard gate above, including the greenfield distinction.
- Prototype impact is recorded and no existing prototype was edited without user confirmation; only deliverable-allowlist files were modified.
- The final handoff names changed files and verification performed, notes limitations, and gives the readiness conclusion in plain language.
